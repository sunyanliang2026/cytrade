# 大单打板策略设计方案

## 1. 策略定位

本策略用于人工指定股票池中的涨停打板交易。股票池不使用问财、韭研公社或其他自动选股来源，而是由人工维护 CSV 文件。

策略只关注涨停价买入委托。当 Level2 中出现符合规则的大额涨停价买单时，立即提交我方买单，并记录我方订单在可观测委托流中的相对位置，供成交概率判断和事后复盘使用。

本策略与 `MainSealFollow` 的区别：

- `MainSealFollow` 关注已经形成封板后的排队跟随和主单留撤。
- 本策略关注新增涨停价大单，出现信号后主动打板。
- 本策略不依赖自动股票池。
- 本策略第一阶段只做 dry-run 和数据验证，不自动开启实盘。

## 2. 股票池

股票池由人工维护，文件放在本策略目录的 `data/` 下，例如：

```csv
code,plan_amount
600001,50000
000001,50000
```

字段定义：

| 字段 | 含义 | 要求 |
|---|---|---|
| `code` | 股票代码 | 支持 6 位代码及带市场后缀的代码 |
| `plan_amount` | 计划买入金额 | 用于计算实际买入数量 |

不增加 `enabled` 字段。CSV 中的有效记录都参与策略运行；需要停止某只股票时，人工从文件中删除该行或单独生成新的股票池。

股票池加载后应执行：

1. 代码归一化和市场识别。
3. 去重。
4. 计划金额和可买数量校验。
5. 为每只股票建立独立策略实例。

## 3. Level2 数据

涨停价必须使用当日 QMT 明确提供的价格：优先读取 `get_instrument_detail().UpStopPrice`，其次读取当日 full tick 的涨停价字段。若两者都不可用，策略不会用涨跌幅规则推算涨停价，也不会触发下单。

竞价阶段（09:15:00 至 09:29:59）的 L2 委托只保存为原始复盘数据，不参与大单触发；只有事件时间不早于 09:30:00 的连续竞价委托才允许触发打板。

策略需要在下单前订阅目标股票的：

- `l2quote`：确认当前价、买一价、涨停价和封板状态。
- `l2order`：识别新增委托，是主要触发数据。
- `l2transaction`：识别成交和撤单，更新队列剩余量。
- `l2orderqueue`：记录买一可见队列和前 50 笔结构，如数据可用则作为辅助定位信息。

不能等检测到大单后才订阅 L2，否则大单前已经存在的排队委托可能无法记录。

### 3.1 关注范围

只处理以下委托：

```text
委托方向 = 买入
and 委托价格 = 当前涨停价
```

非涨停价买单、卖单不触发打板，但可以按需要记录为背景数据。

### 3.2 大单判定

低价股阈值为涨停价小于 8 元：

```text
单笔涨停价买单金额 >= 150 万元
```

非低价股阈值为涨停价大于等于 8 元：

```text
涨停价 >= 8 元 and 委托金额 > 500 万元
```

完整触发条件为：

```text
买入方向
and 委托价格 = 涨停价
and (
    单笔涨停价买单金额 >= 150 万元
    or
    涨停价 >= 8 元 and 委托金额 > 500 万元
)
```

其中：

```text
委托金额 = 委托价格 × 委托数量
```

`10000 手`是实际观察中的单笔规模参考，不是过滤条件，也不对委托数量做上限截断。超过 10000 手的委托仍按实际数量记录，并可额外标记为超大单。

## 4. 触发和下单

未封板启动的股票还必须先经过开盘下探确认：记录到有效开盘价后，当日最低价必须严格小于 `开盘价 * 0.985`，之后出现符合条件的涨停价大单才允许触发下单。该条件用于确认股票曾经下探并出现承接资金拉起；尚未满足时的大单只记录、不下单。启动时已经封板并经过开板后进入 `WAIT_RESEAL` 的回封路径不检查此条件。

### 4.1 启动时已封板

策略拿到首条含有效 `last_price` 或 `bid1` 的报价后判断启动状态：若价格等于准确涨停价，进入 `WAIT_REOPEN`。该状态下的涨停价买单只落盘，不触发下单。

当后续 `last_price` 或 `bid1` 低于涨停价时，记录开板并进入 `WAIT_RESEAL`。此后重新出现的、满足大单阈值的涨停价买单才允许触发下单。若启动时未封板，策略直接进入 `READY`，维持原有触发逻辑。

首条报价没有有效价格时，策略继续等待，不会将其误判为未封板。

大单事件确认后立即提交买单，不设置额外等待确认窗口。

基本流程：

```text
收到 l2order
    -> 归一化价格、方向、数量、金额和委托号
    -> 判断是否为涨停价买单
    -> 判断低价股/非低价股大单条件
    -> 记录触发事件和队列快照
    -> 立即提交我方涨停价买单
    -> 绑定我方订单与触发时的队列定位信息
```

下单数量由 `plan_amount` 按涨停价计算，并符合 A 股 100 股整数倍要求。实际下单前仍必须经过统一交易执行器和运行时安全检查。

## 5. 我方订单的队列定位

核心目标是估算：

```text
我方订单提交时，前面已经有多少有效买单、多少手、多少金额。
```

每次我方下单都要建立一个队列定位点，记录：

| 字段 | 含义 |
|---|---|
| `order_uuid` | 系统本地订单号 |
| `xt_order_id` | QMT 返回的订单号 |
| `entrustNo` | 如果可以匹配，记录对应 Level2 委托编号 |
| `code` / `name` | 股票代码和名称 |
| `submit_time` | 我方提交时间 |
| `price` | 委托价格 |
| `quantity` | 委托数量 |
| `front_order_count` | 我方前方可观测委托笔数 |
| `front_volume` | 我方前方可观测委托总股数/手数 |
| `front_amount` | 我方前方可观测委托总金额 |
| `match_confidence` | 我方订单和 L2 委托匹配的置信度 |

前方有效排队量计算为：

```text
有效前方数量 = 原始前方委托数量 - 已确认成交数量 - 已确认撤单数量
```

前方委托只统计同一股票、同一涨停价、同一买入方向的委托。

## 6. 相邻委托记录

为了让人工在完整队列中定位我方订单，需要记录我方订单前后的相邻委托。

相邻委托按 Level2 委托事件顺序记录：

```text
relative_index=-3  前方委托
relative_index=-2  前方委托
relative_index=-1  前方委托
relative_index=0   我方委托
relative_index=+1  后方委托
relative_index=+2  后方委托
```

每笔相邻委托记录：

- `order_uuid`
- `relative_index`
- `entrustNo`
- 委托时间
- 价格
- 买卖方向
- 数量和金额
- 是否大单
- 后续成交数量
- 后续撤单数量
- 当前剩余数量

默认建议下单时记录我方前后各 5 笔，并同时保存我方下单前后 3 秒内同价买单事件。这个数量和时间窗口属于可配置参数，后续可以根据实际 L2 推送密度调整。

需要明确：相邻委托是可观测委托流中的相对位置，不等同于交易所完整队列的绝对排名。若 L2 事件存在延迟、丢失或订阅启动较晚，记录中必须标明观测不完整。

## 7. 成交概率参考

封板后通常可能成交 5000 万到 1 亿元，这是经验参考，不是大单触发门槛，也不是硬性过滤条件。

策略应记录封板后的动态成交能力：

```text
sealed_limit_trade_amount
```

表示封板状态下的涨停价累计成交金额。

```text
recent_trade_amount
recent_trade_rate
```

分别表示最近观察窗口的成交金额和成交速度。

可以估算我方前方队列的消耗时间：

```text
estimated_time_to_consume_front =
    front_amount / recent_trade_rate
```

成交概率分析至少输出：

- 我方前方剩余委托金额。
- 我方前方剩余委托数量。
- 封板后累计成交额。
- 最近 1 分钟成交额。
- 最近 5 分钟成交额。
- 最近成交消耗速度。
- 前方成交金额。
- 前方撤单金额。
- 预计轮到我方所需时间。

`5000 万到 1 亿元`可以作为经验区间显示：

```text
expected_sealed_trade_amount_low = 50000000
expected_sealed_trade_amount_high = 100000000
```

实际判断仍需结合前方排队量、成交速度和撤单速度，不能仅因为累计成交额达到 5000 万就认定我方必然成交。

## 8. 撤单和重新触发

允许大单撤单后重新打板。

委托生命周期按委托编号跟踪：

```text
大单出现
    -> 我方立即下单
    -> 记录本轮触发委托号
    -> 触发大单撤单
    -> 结束本轮触发锁定
    -> 新的符合条件委托可以再次触发
```

必须使用 `entrustNo` 去重，避免同一笔 Level2 委托重复推送导致重复下单。

第一版建议的重触发边界：

- 触发大单撤单，但我方订单尚未成交且已经撤销：允许新的大单再次触发。
- 同一触发委托的重复事件：不重复触发。
- 我方订单已经全部成交：默认不再重复买入，避免无意加仓。
- 我方订单部分成交：默认不再新增买入，只继续跟踪剩余订单状态。

“大单撤单后可以重新触发”和“我方订单成交后允许加仓”是两个不同规则，后者暂不默认开启。

## 9. 状态机

| 状态 | 含义 |
|---|---|
| `WAIT_SIGNAL` | 等待符合条件的涨停价大单 |
| `ORDER_DETECTED` | 已识别大单，正在保存队列定位信息 |
| `BUY_SUBMITTED` | 我方买单已经提交 |
| `BUY_PENDING` | 等待我方订单成交、撤单或拒单回报 |
| `BUY_PARTIAL_FILLED` | 我方订单部分成交，默认不再加仓 |
| `BUY_FILLED` | 我方订单全部成交，当前股票本轮结束 |
| `BUY_CANCELED` | 我方订单撤单完成，可以等待新的大单 |
| `ERROR` | 数据、订单或状态异常 |
| `EXITED` | 策略结束 |

## 10. 输出和日志

每次触发至少记录：

- 股票代码和名称。
- 触发 Level2 委托编号。
- 涨停价。
- 委托数量、手数和金额。
- 低价股或非低价股判定分支。
- 我方订单号。
- 我方订单前方笔数、数量和金额。
- 相邻委托列表或关联输出文件。
- 当前封板累计成交额。
- 最近成交速度。
- dry-run 状态。

建议输出两张表：

`order_queue_snapshot.csv`：每次我方下单时的前方队列摘要。

`order_queue_neighbors.csv`：我方订单前后的相邻委托明细。

原始 Level2 数据应按股票、日期和数据类型持续落盘，至少保留 `l2quote`、`l2order`、`l2transaction`、`l2orderqueue` 原始字段，便于事后复盘和定位丢单问题。

## 11. 安全边界

- 新策略默认 dry-run。
- 不修改 `MainSealFollow` 的实盘开关。
- 不自动修改账号、QMT 路径、Cookie 或本地运行配置。
- 不绕过统一交易执行器、资金检查、数量检查和交易就绪检查。
- 任何切换实盘、调整仓位上限或允许成交后加仓的变更，都需要人工明确确认。

## 12. 实现顺序

1. 建立独立策略目录、人工股票池格式和读取校验。
2. 接入现有 L2 事件订阅和原始数据落盘。
3. 实现涨停价买单和两档大单判定。
4. 实现委托编号去重和触发事件日志。
5. 实现我方订单与 Level2 委托的匹配。
6. 实现前方有效委托量和相邻委托记录。
7. 实现成交、撤单和重新触发状态机。
8. 实现封板成交额、成交速度和预计消耗时间统计。
9. 先用回放数据和 dry-run 验证，再评估是否需要实盘参数。

## 13. 待确认参数

以下参数当前只记录设计意图，实施前需要最终确认：

- 我方订单前后相邻委托默认记录笔数。
- 下单前后关联委托的时间窗口。
- 我方订单无法与 Level2 `entrustNo` 直接匹配时的匹配规则。
- 我方订单部分成交后是否允许人工配置为继续加仓。
- 撤单后重新触发是否需要最短冷却时间。
- 成交概率输出使用最近 1 分钟、3 分钟还是 5 分钟作为主速度窗口。
