## 后续运行的自动采集

现有实盘和market-only入口下次启动会自动开启诊断，当前已运行进程不会加载新代码。输出在 `data/latency_diagnostics/YYYY-MM-DD/HHMMSS_PID/`，结束自动生成 `analysis.md` 和 `analysis.json`。主进程逐段计时、独立同池探针、每秒QMT缓存进度、CPU/线程/磁盘/时钟、异常线程现场和白名单QMT日志均保留。每笔实际下单精确匹配触发委托，报告同时显示行情、SDK接收、本地提交与柜台原始时间。

实测发现 `count=-1` 启动时会补发订阅之前的记录：14:14启动的一次测试收到13:57的委托。这不能直接称为实时延迟。新诊断单独统计订阅前既有记录，不把其行情年龄混入实时延迟；其处理耗时仍检查，以便判断历史补发是否造成积压。09:23启动后产生的09:31触发委托不属于这类启动历史记录。

预期复盘应给出可核实的本地瓶颈，或将问题定位到SDK/QMT边界并指出仍需券商提供的证据。不得承诺在缺少逐条网络接收时间的情况下必然区分上游与QMT内部接收原因。

## 独立探针

```powershell
.\strategies\large_order_limit_up_buy\scripts\probe_l2_latency.bat --stocks "002733,002242" --duration 180 --compare-strategy
```

该入口不创建策略、不连接交易账户、不下单，也不会取消其他进程的订阅。退出时只注销本次取得的订阅ID。

输出目录：`data/latency_probe/YYYY-MM-DD/HHMMSS_PID/`，相对于本策略目录。

- `callbacks.csv`：逐笔行情身份与SDK接收、解码时间。
- `cache.csv`：QMT缓存进度与读取时间；空时间表示没有缓存，不能当成0延迟。
- `session.json`：订阅耗时、记录数、丢包、异常、实际起止时间。
- `comparison.csv`：自动匹配当日策略原始记录，中文逐笔对照表。
- `comparison.json`：按股票和行情类型汇总对照结果。

## 如何判读

1. 同一行情探针明显早于策略：定位策略进程的SDK分发、GIL、回调及写盘负担。
2. 探针也晚收到，而更早的QMT缓存采样进度已超过该行情：优先查QMT缓存到SDK的分发路径。
3. 探针和缓存同时晚：还需QMT原始网络接收时间，不能直接归因网络或券商。
4. 正常时段的样本只能说明该时段；下午正常不能证明早盘已经解决。下一交易日仍需在开盘前同时启动探针和策略。

现有QMT日志没有给出三笔触发委托对应的原始网络包首次接收时间，暂不能精确分摊早盘延迟。午休、收盘、股票没有新委托时，行情年龄自然增长，不应作为网络延迟。
