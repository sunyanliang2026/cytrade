# 大 QMT 原生 Python 重写经验手册

本文记录本次将策略从外部 Python/qmtmini 形态重写为大 QMT 内置原生 Python 模型的过程，作为后续策略重写和现场验证的模板。

## 1. 先拆分边界

开始编码前先完成三件事：

1. 阅读设计文档、现有策略和部署说明，列出已经实现、待实现和不能改变的交易规则。
2. 明确本次重写只负责原生 QMT 入口、行情订阅、状态机和交易回报；不顺手修改账户配置、仓位规则或下单开关。
3. 把每个模型放在 `strategies/rewrite/<model_name>/` 下，入口、设计文档、数据示例和测试放在同一个子目录；不同模型之间不共享可变状态。

推荐的目录形态：

```text
strategies/rewrite/
  <model_name>/
    QMT_<MODEL_NAME>.py
    DESIGN.md
    QMT_NATIVE_NOTES.md
    data/
    tests/
  README.md
  CHANGELOG.md
  REWRITE_PLAYBOOK.md
```

## 2. 原生 QMT 的硬约束

- 入口使用 `init(ContextInfo)`、`handlebar(ContextInfo)`、`stop(ContextInfo)`，以 QMT 调度为准。
- 原生模型按单线程处理。回调内不能创建线程池、等待 Future、`sleep`、做网络等待或长时间重试。
- 把较重的工作拆成小片段，通过 `schedule_run` 或下一次 `handlebar` 继续执行，让出控制权。
- 回调参数可能是深拷贝对象，并且在回调结束时回滚。跨回调状态必须存放在脚本自己的全局容器中，不能写回 `ContextInfo` 或行情参数。
- 回调中只做快速复制、计数、状态转移和必要的下单调用；文件写入、批量分析和诊断输出应分片完成。
- `stop` 必须取消所有定时器和行情订阅，避免旧模型继续消费行情或重复下单。

## 3. 路径、编码和 QMT 环境

- QMT 原生入口通常保持 `# coding: gbk`，以兼容内置编辑器；离线辅助文档和测试使用 UTF-8。
- 原生执行环境可能没有 `__file__`。路径解析顺序应覆盖：脚本目录（存在时）、当前工作目录、QMT 安装目录和 `bin.x64` 目录。
- 启动日志要打印 `cwd`、`__file__` 是否存在、实际脚本路径、股票池路径、策略日志路径和原始行情日志路径。
- CSV 股票池使用 UTF-8-SIG 读取，允许六位代码并自动补充 `.SH` 或 `.SZ`；找不到股票池时应明确打印候选路径。
- 不要因为本地开发路径存在就假设 QMT 原生环境也存在同一路径。

## 4. 行情订阅和状态设计

先按策略必需数据订阅，调试数据单独开关控制：

- `tick`：普通行情和价格时间戳。
- `l2quote`：盘口、封单和涨停状态。
- `l2order`：大单触发、撤单/回封等订单流信号。
- `l2quoteaux`、`l2transaction`、`l2transactioncount`、`l2orderqueue` 只有在诊断确实需要时才订阅。

每个股票的运行状态、首次行情、下单 token、订单号、成交累计量、撤单状态和计时器都放在全局实例字典中。行情回调先深拷贝 payload，再写入自有缓冲区；不能依赖回调参数在下一次回调中继续存在。

盘中任意时刻都可能启动模型：

- 只有在竞价时间窗内才处理竞价快照。
- 连续竞价启动时，如果股票已经在涨停价，不把它当成启动后的首封，进入 `WAIT_REOPEN`，等待开板后的重新回封。
- 启动时已满足跳过条件的股票要记录原因，例如开盘涨幅不合格或缺少有效昨收价。

## 5. 延时和首封验证

L2 原始 JSONL 每条记录至少保留：股票、周期、原始 `data`、格式为 `HH:MM:SS.mmm` 的 `received_time` 和 `event_time`，以及解析后的 `latency_ms`。内部仍使用未格式化的接收时间和 QMT 时间戳计算延时，但不把这些辅助字段写入落盘记录。延时统计规则如下：

- 优先使用 QMT 的毫秒级 `time`；`stime` 只用于显示和交易时段判断。
- 缺失、秒级、不可解析或早于接收时间的时间戳不纳入延时统计，并记录排除原因。
- 按周期和股票分别统计有效样本数、超过 1000 ms 次数、平均值、P95、最大值和最近值。
- 大单策略仅订阅 `l2quote`、`l2order`：前者超过 2 秒打印限频告警，后者保留 1 秒重点监控；汇总按两类周期分别打印延时。`get_full_tick` 启动快照不等同于 tick 实时订阅。
- 若需比较 `tick` 和 `l2quote` 的接收先后，应通过独立探针在相同观察窗口中按股票配对，避免在生产策略中额外增加 tick 回调负载；配对结果只表示“模型启动后的首次观察”，不等于交易所当日历史首封，应跨多个交易日和多个股票积累样本后再评估。

大单策略用 `l2quote` 维护最新报价、昨收对比和封板盘口状态，用 `l2order` 识别逐笔委托信号；其他模型应按自己的状态机选择行情周期，并用运行日志核实字段和时延。

## 6. 原生下单和异步回报

下单前先用当前券商 QMT 的 `xtconstant.py` 核对方向、委托类型、价格类型和持仓查询类型。典型原生调用为 11 个参数：

```python
passorder(23, ORDER_TYPE_BUY, ACCOUNT_ID, code,
          PRICE_TYPE_LIMIT, price, quantity,
          STRATEGY_NAME, 2, user_order_id, ContextInfo)
```

注意事项：

- `user_order_id` 后面紧跟 `ContextInfo`，不要插入多余的空字典或占位参数。
- 订阅回调、定时器回调中的即时委托使用 `quickTrade=2`；逐 K 线 `handlebar` 下单再按信号生效时机选择参数。
- 下单返回值只代表请求是否被接受，不代表已获得订单号或已经成交。
- 回调可能先于订单号查询到达。用唯一的待提交 token、代码、价格和数量做唯一匹配，订单号补齐后再绑定。
- `order_callback` 处理委托状态、原始委托量、累计成交量和订单号；`deal_callback` 处理成交 ID、成交量、成交价和证券市场。
- 以成交 ID 去重，按成交回报累计量更新策略状态，并与订单侧累计量交叉校验，避免重复回调造成重复计数。
- 明确处理撤单中、部分撤单、完全撤单、成交和废单等状态；异步回报关联失败必须打日志。
- 每个模型都应明确记录 `ENABLE_LIVE_ORDERS` 和 `ACCOUNT_ID` 的部署值。当前打板、卖出模型默认实盘开启，账号为 `32011276`；测试代码须独立覆盖配置，避免测试触发真实委托。

## 7. 隔夜定时模型的特殊处理

隔夜模型的目标是按时间尽快提交计划单，不应把外部交易日接口作为硬阻断条件：

1. 到达启动时间后先分片完成 CSV、价格、数量、资金和重复提交检查。
2. 预检查完成后立即打开提交窗口，逐行分片调用 `passorder`。
3. 用状态文件保存批次号、交易日、行号和提交 token，防止模型重启重复提交。
4. 第二次启动如果发现同一交易日已有提交预约，只记录并停止，不再次下单。
5. 提交后保持回调监控，直到订单回报或模型停止；不要因为启动时间变化而重复建立批次。

## 8. 验证顺序

每次改动按以下顺序验证：

1. 离线编译：用本机 Python 验证语法，再用 QMT 支持的 Python 版本做兼容检查。
2. 单元测试：覆盖路径解析、订阅结果、首封配对、`passorder` 参数数量、异步订单绑定、成交去重和状态转移。
3. 原生入口验证：在测试环境隔离真实下单，确认 `init` 能执行、订阅返回值正常、关键回调都出现。
4. 交易时段运行：记录 QMT 策略日志、主日志、原始 JSONL、订阅成功/失败、回调计数、缓冲区长度和延时汇总。
5. 下单验证：按当前授权和部署配置核对委托回报、成交回报、撤单回报和账户持仓变化。
6. 收尾检查：运行 `git diff --check`，确认没有覆盖用户已有未提交文件，并把证据、问题和验证结果追加到 `CHANGELOG.md`。

## 9. 现场排查优先级

出现“无法连接行情服务”时，先区分收盘后服务不可用和代码错误：

1. 确认 QMT 行情服务已登录且处于交易时段。
2. 看订阅返回值，再看是否收到每个周期的首条回调；不能只看订阅成功数字。
3. 对照策略日志、QMT 主日志和原始 JSONL 的时间戳，判断是服务无数据、回调积压还是本机时钟不准。
4. 检查单线程回调是否做了阻塞工作，以及缓冲区是否持续增长。
5. 只有证据表明策略判断错误时，才修改状态机或阈值；行情服务问题不要通过改变交易逻辑掩盖。
