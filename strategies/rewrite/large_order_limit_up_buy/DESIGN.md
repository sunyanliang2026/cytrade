# 设计映射

本文把 `strategies/large_order_limit_up_buy/docs/design.md` 中的需求映射到当前原生脚本。原设计文档仍是策略规则的来源；本文件记录原生实现的边界和尚未完成的部分，避免后续迭代把“已实现”和“待实现”混在一起。

## 运行结构

`init(C)` 创建每只股票的独立实例、读取 CSV、取得初始行情、建立订阅并启动定时器。策略允许在交易日盘中任意时间启动：竞价窗口内使用有效竞价快照，连续竞价中启动则以第一条有效 `l2quote` 判断当前是否已封板。行情回调按股票代码闭包分发到实例；`handlebar(C)` 负责验证定时器兜底和周期汇总；`stop(C)` 取消任务、刷新原始缓冲区、取消订阅并关闭日志。

全局 `_INSTANCES` 是跨回调状态的唯一容器。实例保存涨停价、昨收、开盘价、当日最低价、封板周期、大单去重集合、订单号和验证状态。回调收到的数据先经过 `copy.deepcopy`，再写入实例或原始缓冲区。

## 状态机

```text
WAIT_INITIAL_QUOTE
  ├─ 09:25 快照买一=涨停价 -> WAIT_REOPEN
  ├─ 09:25 快照买一<涨停价 -> READY
  └─ 快照无效 -> 保持 WAIT_INITIAL_QUOTE，等待有效 L2 quote

READY
  └─ 买一涨停、封单>6000万、涨停大单累计>1000万、开盘后低点<开盘价*0.985
       -> 首封下单

WAIT_REOPEN
  └─ 封板>10秒且峰值>=1亿元，开板>=3秒后再次封板
       -> 回封下单并进入验证

下单后的回封验证
  ├─ 150笔内出现2笔>=150万元 -> 验证通过，订单保持有效
  ├─ 满150笔且本地经过>=1秒 -> 请求撤单，进入5秒补充观察
  └─ 成交、撤单失败、状态未知或窗口结束 -> DONE
```

时间戳只用于判断竞价和连续竞价范围；验证时长、订单号查询重试和回封周期使用 `time.monotonic()` 或 QMT 定时器，不用行情时间戳计算经过时间。

## 行情与原始数据

当前策略默认只订阅 `tick`、`l2quote` 和 `l2order`。`l2quoteaux`、`l2transaction`、`l2transactioncount` 和 `l2orderqueue` 不参与策略判断，改由独立诊断探针按需订阅。所有已订阅回调的原始数据进入有界内存缓冲区，再由一秒周期的 `schedule_run` 每次刷新有限条数；缓冲区满时丢弃最旧记录并累计计数。原始记录包含接收墙钟、股票代码、周期和序列化后的数据。

策略判定使用三类数据，各自职责固定：

- `tick` 只维护开盘价、昨收、当日最低价和普通行情兜底，不直接触发首封或回封。
- `l2quote` 只负责封板状态、买一封单量和涨停价比较；封板只比较 `bid1` 与精确涨停价，封单金额按 `价格 * 手数 * 100`。
- `l2order` 负责首封大单、回封验证和委托去重。
- 竞价期间只保存数据，不产生连续竞价信号。
- 09:25:00 至 09:25:05 每秒批量重试 `get_full_tick`；无效快照不会阻塞整池运行。
- 09:30 后开始累计当日最低价，并在最低价低于昨收时将实例标记为 `SKIPPED_OPENING_GAIN`，关闭其验证任务。

连续竞价中启动时，第一条有效 `l2quote` 若已在涨停价，实例进入 `WAIT_REOPEN`，从启动后重新观察封板、开板和回封；若未在涨停价，实例进入 `READY`，后续涨停才可进入首封路径。这样不会把启动前已经发生的封板持续时间或大单累计伪装成可验证的首封。

## 交易回报

实盘开关开启且通过账号检查后，脚本使用完整的 `passorder` 参数提交限价买单；订单号缺失时用 `get_last_order_id` 通过一次性定时器重试查询。`order_callback(ContextInfo, orderInfo)` 和 `deal_callback(ContextInfo, dealInfo)` 只更新全局实例，不把状态挂在回调参数上。回封验证撤单调用 `cancel(order_id, account_id, account_type, C)`。

## 当前差异和后续工作

以下内容来自原设计，但当前脚本仍需独立验证或补齐，后续修改必须先补测试和日志证据：

- 原设计要求的“开盘涨幅低于 3.5%”筛除尚未形成独立计算路径；当前已实现的是连续竞价最低价低于昨收的剔除。
- 当前原始数据已经落盘，但尚未生成设计中完整的 `post_order_30s_orders.csv`、前后相邻委托和队列汇总报告。
- 策略默认已只保留 `tick`、`l2quote` 和 `l2order`；完整 L2 周期只在独立诊断探针中启用。
- 需要在真实交易时段继续验证 QMT 对每个 L2 周期的回调字段、回调频率、行情时间戳和原始 JSONL 写盘延迟。

## 调试观测

验证阶段 `DEBUG_SUMMARY_INTERVAL_SECONDS` 为 60 秒。`init` 会输出实际脚本、工作目录、`__file__`、股票池和两类日志路径；订阅阶段逐项输出返回的订阅号和成功/失败计数。每个周期的第一条行情只输出一次 `[回调首条]`，原始 JSONL 同时保存 `received_at`（本机接收墙钟）、`event_time`（QMT 行情时间）和计算出的 `latency_ms`。延时优先使用 QMT 的 `time` 时间戳，策略时段判断仍使用 `stime`。延时超过 1000ms 时按周期每 10 秒最多提示一次；周期汇总显示每类行情的有效样本/总样本数、超限次数、平均/最大/最近延时，以及逐股票聚合的回调间隔均值/最大值，用于对比 `tick` 与 `l2quote`。仅对带毫秒精度的事件时间计算延时；缺少时间或事件时间晚于接收时钟的样本不纳入延时统计。该观测只读，不改变策略阈值、账户或下单逻辑。

涨停首报诊断分别记录每只股票首次观察到 `tick.bid1 == 涨停价` 和 `l2quote.bid1 == 涨停价` 的接收时刻，并在两路齐全后输出先到周期和接收差值。只统计连续竞价的订阅回调；盘中启动后已经封板的股票记录的是启动后的首次观察，不代表当天首次触板。用覆盖数、配对数、先到次数和配对差值跨多个交易日评估两路表现。
